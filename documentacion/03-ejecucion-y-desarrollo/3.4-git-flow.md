## 2. Ramas (Git Flow adaptado)

El remoto ya usa `main` como rama viva del prototipo. No creamos `develop` a destiempo ni movemos tags viejos.

| Rama | Para qué | Ejemplo |
|---|---|---|
| `main` | Integración demostrable. Solo entra código revisado. | `main` |
| `feature/HU-xx-slug` | Una historia Must del [1.3](../01-analisis/1.3-historias-de-usuario-y-product-backlog.md) o un arreglo acotado. | `feature/HU-06-catalogo-filtros` |
| `hotfix/…` | Parche urgente sobre `main` (runtime, CORS, cookie). | `hotfix/sid-cookie` |

```bash
git checkout main
git pull origin main
git checkout -b feature/HU-08-postularse
# …trabajo…
git push -u origin HEAD
# En GitHub: Open pull request → base main
```

Una rama = una HU (o un arreglo). Si el cambio toca dos historias, el título del PR nombra la HU principal y el cuerpo lista la otra.

## 3. Commits

Español, **presente**, una idea por commit. El mensaje dice *por qué* y lleva el ID de la HU.

```
Cierra HU-02: deja GET /auth/yo en 200 cuando no hay cookie sid
Ajusta HU-11: el donante reserva el ítem sin recaudo
Documenta el tablero de ejecución de las HU Must
```

No usamos mensajes vacíos (`update`, `fix`, `wip`). No mezclamos un CRUD nuevo con un rediseño de `estilos.css` en el mismo commit.

---

## 4. Pull requests

1. La rama sale de `main` actualizado.
2. El PR describe HU, pantallas y rutas de API.
3. El otro aprendiz revisa (comentario o approve).
4. Se fusiona con merge commit (no rebase de `main`).
5. Se borra la rama remota.

Plantilla mínima del cuerpo:

```
## HU
HU-0X — título del 1.3

## Qué se puede demostrar
Pantalla / ruta API / cuenta de piloto

## Cómo probar
Pasos en http://localhost:5173
```

## 5. PR #1 de Brayan: no fusionar a ciegas

[PR #1](https://github.com/juliodparada-bit/plataforma-refugios-fauna-domestica-bogota/pull/1) — `fix(HU-D1): corrige tamaño de radios y alineación de checkboxes` — rama `feature/HU-D1-fix-checkboxes-registro`. Quedó **cerrado**, no mezclado.

Ese PR toca el registro (`Registro.tsx` / estilos de radios y checkboxes). Julio tiene en local un rediseño sin commitear de `web/src/estilos.css` y pantallas nuevas (Inicio, Necesidades, Cuenta). **Fusionarlo ahora sobre ese árbol pisa el look pastel/neon y abre conflictos.**

Cómo integrarlo bien, cuando Julio commitee su rediseño:

1. Julio publica su trabajo en `feature/HU-xx-…` y lo mete a `main` por PR.
2. Brayan rebasea o reabre una rama nueva desde ese `main`.
3. Se reabre o se abre un PR nuevo, se resuelven conflictos en `estilos.css` juntos, y entonces sí se mezcla.

Hasta ese momento el PR #1 **es evidencia de que Brayan programa**; no es un merge pendiente de un clic.

## 6. Qué no hacemos

- `git push --force` a `main`.
- `git reset --hard` del árbol de trabajo de Julio.
- Commits viejos inventados para “llenar” el log.
- Mezclar el PR #1 encima del rediseño local.
- npm desde la raíz del repo (cada paquete vive en `api/` o `web/`).
