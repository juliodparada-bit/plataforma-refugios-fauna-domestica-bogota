## 1. Estilo arquitectónico

**Cliente-servidor en tres capas lógicas**, con **un solo backend** y dos clientes de presentación.

| Capa | Responsabilidad |
|---|---|
| Presentación | Cliente web React (Chrome, Firefox o Safari; menú abajo en celular y arriba en escritorio según el **ancho del viewport**) y companion Flutter en `mobile/` (mismas reglas de negocio). |
| Aplicación (API) | Autenticación, reglas de negocio (especie, estados, puntaje, permisos por rol). Un solo backend. |
| Persistencia | PostgreSQL (datos) + almacén de archivos (fotos y evidencias). |

No hay capa de pagos. Flutter no es un segundo sistema: consume la misma API Nest. La web transporta el JWT en cookie `httpOnly` `sid`; la app lo envía como `Authorization: Bearer`. El canal de difusión sigue siendo la URL (formulación 6.3).

El puntaje de compatibilidad es un **módulo de reglas** dentro de la API (RF-09), no un servicio de aprendizaje automático.

## 4. Stack del prototipo

Elegido para el equipo de la ficha (Julio David Parada León y Brayan Alejandro Sánchez) y para cumplir el IEEE 830 con **un backend** y dos clientes. **Si el centro ADSO exigiera Java**, las capas no cambian: Spring Boot sustituye a Nest; PostgreSQL se queda.

| Pieza | Tecnología | Por qué |
|---|---|---|
| Cliente web | React 19 + Vite 6 + TypeScript | SPA responsive; Vite hace de proxy `/api` en local. TypeScript comparte el contrato de roles con la API. |
| Cliente móvil | Flutter 3 (Dart) en `mobile/` | Companion de las mismas HU; no es un segundo backend. |
| API | Node.js + NestJS 11 + TypeScript | Módulos = dominio (auth, verificación, animales, postulaciones, deseos). Guards de sesión y rol en el servidor (RF-21). |
| Mapeo | Prisma | El `schema.prisma` es el DER del 2.3 en el repo. Las migraciones viajan con Git. |
| Datos | PostgreSQL 16 | FK y CHECK de especie; no Mongo «por probar». |
| Archivos | Disco local (`uploads/`) | Fotos y evidencias. S3 queda para un piloto posterior. |
| Identidad | JWT firmado (bcryptjs costo 12). Web: cookie `httpOnly` `sid`. Móvil: `Authorization: Bearer` | RF-01 y RF-02. `extraerToken` en `api/src/auth/token.ts`: si hay ambas, gana la cookie. |
| Contenedor de datos | Docker / Podman (`compose.yml`) | Postgres en el puerto 5433. |
| Control de versiones | Git + GitHub | Evidencia de ejecución ADSO. |

**Motor de datos:** PostgreSQL en ambos caminos (Nest o Spring). No se usa un motor distinto «por probar».

## 5. Decisiones que la arquitectura debe hacer cumplir

Estas reglas viven en la API, no solo en botones de la interfaz.

1. `especie` solo `canino` o `felino` (RF-07).
2. Una entidad no publica hasta verificación aprobada (RF-03, RF-04).
3. No existen módulos ni tablas de recaudo, pasarela ni apadrinamiento.
4. La bitácora pública de insumos no expone datos personales del donante (RNF-02).
5. El puntaje se calcula con las cinco respuestas de estilo de vida y se devuelve con una frase explicable (RF-08, RF-09).
6. TLS (HTTPS) es el criterio de piloto (RNF-01). La sustentación local corre en HTTP: web `5173`, API `3000`.

## 6. Tres superficies, dos clientes, una API

Detalle de pantallas: [2.4 Interfaz](2.4-interfaz-ui-ux.md). Aquí fijo que **no** son tres backends distintos. Web y Flutter cubren las mismas superficies:

1. **Pública:** Inicio (tres caminos), catálogo, perfil de animal, badge y bitácora de la entidad.
2. **Adoptante / donante:** cuestionario, postulaciones, necesidades (listado `GET /entidades`) y reservas. El donante aterriza en Necesidades, no en el catálogo.
3. **Entidad / validador:** solicitud de verificación, cola, alta de animal, tablero de postulaciones, deseos. Publicar exige sello.
