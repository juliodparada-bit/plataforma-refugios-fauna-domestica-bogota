## 1. Introducción

### 1.1 Propósito

Definir los requisitos funcionales y no funcionales del sistema, de modo que puedan diseñarse, construirse y probarse sin ambigüedad. Destinatarios: el aprendiz (Product Owner y desarrollador), el instructor ADSO y, en el piloto, el refugio aliado.

### 1.2 Ámbito del sistema

Sistema de información **web** que permite a entidades de rescate independientes de Bogotá urbana:

- verificarse en dos niveles;
- publicar perros y gatos domésticos con historia;
- recibir postulaciones de adopción con puntaje de compatibilidad por reglas;
- publicar y cerrar listas de deseos de insumos.

No es un marketplace, no recauda dinero y no gestiona fauna silvestre.

**Métrica norte:** cupos liberados por adopción efectiva.

## 2. Descripción general

### 2.1 Perspectiva del producto

Producto **independiente**. No se integra en tiempo de ejecución con sistemas del IDPYBA. Convive conceptualmente con ese ecosistema (complemento, no sustituto). Arquitectura: cliente web + API + PostgreSQL + archivos; detalle en [2.1 Arquitectura](../02-planeacion-y-diseno/2.1-arquitectura-de-la-solucion.md).

### 2.2 Funciones del producto (resumen)

1. Registrar y autenticar usuarios con rol.
2. Recibir y resolver solicitudes de verificación de entidades.
3. Publicar, editar y archivar animales (solo canino/felino).
4. Calcular y mostrar un puntaje de compatibilidad por estilo de vida.
5. Gestionar el ciclo de una postulación hasta la entrega.
6. Gestionar ítems de lista de deseos hasta su cobertura con evidencia.
7. Exponer un badge de verificación y una bitácora resumida de insumos.

### 2.3 Características de los usuarios

| Tipo | Formación / contexto | Actividades en el sistema |
|---|---|---|
| Entidad Nivel 1 o 2 | Variable; suele manejar Instagram y WhatsApp, no paneles complejos | Publicar animales e ítems; revisar postulaciones; confirmar insumos |
| Adoptante | Ciudadano mayor de edad en Bogotá | Cuestionario, consulta de catálogo, postulación |
| Donante | Ciudadano que quiere ayudar sin transferir a un Nequi opaco | Reservar un ítem y esperar confirmación |
| Validador | Operador del piloto (el aprendiz) | Aprobar o rechazar evidencias |

**Implicación de usabilidad:** la interfaz de la entidad debe poder usarse en celular, que es el dispositivo real del rescate informal. El canal de llegada es un enlace (WhatsApp / Instagram), no una instalación en tienda.

### 2.4 Restricciones

- Un desarrollador; stack fijado en la arquitectura 2.1 (NestJS + React + PostgreSQL, o Java/Spring si el centro lo exige).
- Sin pasarela de pagos.
- Almacenamiento de evidencias fotográficas obligatorio (verificación y recepción de insumos).
- El servidor debe rechazar especies distintas de canino y felino aunque la interfaz se manipule.
- Datos personales: minimización; la bitácora pública no muestra cédula ni teléfono del donante.

### 2.5 Suposiciones y dependencias

- Existe al menos un refugio o proteccionista dispuesto a probar el prototipo.
- Los adoptantes tienen correo y navegador web actualizado.
- La coordinación logística de un bulto se hace por fuera del sistema.
- El validador humano existe; no hay motor de IA de verificación.

### 2.6 Fuera de alcance de este ERS

Apadrinamiento, micro-suscripciones, pasarela de dinero y matching estadístico con histórico no forman parte de este sistema.

Las aplicaciones nativas iOS / Android tampoco se especifican aquí. Quedan **pendientes de posible cambio**: el canal comprometido es la web por URL; la nativa se reevaluará como cliente adicional cuando el piloto tenga uso recurrente (formulación, sección 6.3).

## 3. Requisitos específicos

Prioridad MoSCoW: **M** Must (obligatorio), **S** Should (se incluye si el tiempo del prototipo lo permite).

### 3.1 Requisitos funcionales

Cada RF se especifica con descripción, entradas, proceso, salidas y prioridad. Los criterios de prueba detallados viven en las historias de usuario.

Resumen MoSCoW:

| Prioridad | Requisitos |
|---|---|
| Must | RF-01 a RF-05, RF-07 a RF-18, RF-20, RF-21 |
| Should | RF-06 (editar/archivar animal), RF-19 (caducidad de reserva a 7 días) |

#### RF-01 Registrar usuario

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | El sistema permite crear una cuenta con correo, contraseña y rol inicial (adoptante, donante o entidad). |
| Entradas | Nombre, correo, contraseña, rol, localidad en Bogotá, consentimiento de datos personales |
| Proceso | Validar unicidad del correo, almacenar contraseña cifrada, registrar consentimiento |
| Salidas | Cuenta en estado activo; si el rol es entidad, no puede publicar hasta que RF-04 apruebe la verificación |
| Precondición | Correo no registrado |
| Postcondición | Existe un usuario autenticable |

#### RF-02 Autenticar usuario

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | Ingreso con correo y contraseña. Cierre de sesión. |
| Entradas | Correo, contraseña |
| Proceso | Verificar credenciales; crear sesión |
| Salidas | Sesión iniciada o mensaje de error genérico (no revelar si el correo existe) |

#### RF-03 Solicitar verificación de entidad

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | Una cuenta con rol entidad carga datos del albergue y evidencias de Nivel 1 o Nivel 2. |
| Entradas | Nombre de la entidad, localidad, nivel solicitado, archivos de evidencia |
| Nivel 1 | RUT, Cámara de Comercio, certificado de representación legal |
| Nivel 2 | Evidencia de convocatoria/participación IDPYBA **o** carta de veterinaria COMVEZCOL (al menos una) |
| Proceso | Crear solicitud en estado `en_revision` |
| Salidas | Solicitud con identificador; la entidad no publica todavía |

#### RF-04 Resolver verificación

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Actor | Validador |
| Descripción | Aprobar Nivel 1, aprobar Nivel 2, rechazar con motivo o pedir complemento. La visita o video es opcional y solo en casos dudosos. |
| Salidas | Badge visible; permisos de publicación. El sistema no incluye recaudo de dinero. |

#### RF-05 Publicar animal

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Precondición | Entidad con verificación aprobada |
| Descripción | Alta de un animal con historia y datos de convivencia. |
| Campos mínimos | Nombre, especie (`canino` \| `felino`), sexo, talla aproximada, edad aproximada, localidad, historia (texto), energía, convivencia con niños, convivencia con otros animales, esterilización si se conoce |
| Opcionales | Raza (no filtro principal), necesidad especial / discapacidad / trauma, fotos |
| Regla | El servidor rechaza cualquier especie distinta (RF-07) |
| Postcondición | Animal `publicado` si cumple campos mínimos. Un guardado incompleto puede quedar en `borrador` (estado de apoyo del UML 2.2 y del DER 2.3); ese borrador no sale en el catálogo. |

#### RF-06 Editar o archivar animal

| Campo | Contenido |
|---|---|
| Prioridad | S |
| Descripción | La entidad actualiza datos o pasa el animal a `archivado` sin haber adopción. No se borra el historial de postulaciones. |

#### RF-07 Bloquear especies no permitidas

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | Interfaz y API rechazan el registro de fauna no canina ni felina. Mensaje explícito. |
| Postcondición | Cero filas de otras especies en persistencia |

#### RF-08 Cuestionario de estilo de vida

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | El adoptante responde cinco preguntas: tipo de vivienda, horas de compañía al día, niños en el hogar, otros animales, nivel de energía que puede sostener. |
| Postcondición | El perfil de adoptante queda apto para puntaje y postulación |

#### RF-09 Calcular puntaje de compatibilidad

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | El sistema compara las cinco respuestas con los atributos del animal y produce un puntaje más una frase explicable (ejemplo: «coincide en vivienda y energía; no convive bien con gatos»). |
| Restricción | No se usa aprendizaje automático |

#### RF-10 Consultar catálogo

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | Listar animales `publicados`. Filtros destacados: especie y localidad. **No** hay filtro destacado de raza. Ordenación por puntaje si el adoptante ya respondió RF-08; en caso contrario, por fecha de publicación con cupo de visibilidad para perfiles de baja demanda (adultos, mestizos, necesidad especial). |
| Usabilidad anti-sesgo | La historia es protagonista del perfil; la raza, si existe, es dato secundario |

#### RF-11 Ver perfil de animal

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | Muestra historia, atributos de convivencia, badge de la entidad, puntaje si aplica, y llamada a postularse. |

#### RF-12 Crear postulación de adopción

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Precondición | Adoptante autenticado con RF-08 completo; animal `publicado` |
| Entradas | Reutiliza el cuestionario; pide confirmación de mayoría de edad y localidad |
| Postcondición | Postulación en estado `enviada` |

#### RF-13 Gestionar postulaciones

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Actor | Entidad dueña del animal |
| Descripción | Ver postulaciones, puntaje y respuestas; pasar a `en_revision`, `preseleccionada` o `rechazada`. Puede marcar «requiere evidencia extra del hogar» solo si el animal tiene necesidad especial o el refugio lo decide. |

#### RF-14 Entregar adopción y liberar cupo

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | La entidad marca `entregada`. El animal pasa a `adoptado` (deja el catálogo activo). Se incrementa el contador de cupos liberados. Queda activo el seguimiento a 15 días (RF-15). |
| Regla | No se eliminan postulaciones ni el perfil; se archivan |

#### RF-15 Seguimiento a 15 días

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | La entidad registra el resultado del seguimiento (estable, con novedad, retorno). No se automatizan llamadas ni correos masivos; basta el estado en el tablero. |

#### RF-16 Publicar ítem de lista de deseos

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Precondición | Entidad verificada |
| Campos | Categoría (alimento, medicina, aseo), descripción, cantidad, unidad, prioridad |
| Regla | No hay campo de «envía Nequi / valor libre en COP» como llamado a transferencia |

#### RF-17 Reservar ítem

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Actor | Donante autenticado |
| Descripción | Reserva un ítem `pendiente`. Deja dato de contacto para coordinar entrega fuera del sistema. Plazo de caducidad propuesto: 7 días calendario. |
| Postcondición | Ítem `reservado` |

#### RF-18 Confirmar recepción de insumo

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Actor | Entidad |
| Descripción | Confirma con evidencia (foto o check de recibido). Ítem pasa a `cubierto`. La bitácora pública muestra el ítem y la fecha, **sin** datos personales del donante. |

#### RF-19 Caducidad de reserva

| Campo | Contenido |
|---|---|
| Prioridad | S |
| Descripción | Si no hay confirmación en el plazo, el ítem vuelve a `pendiente` y la reserva queda `vencida`. |

#### RF-20 Consultar badge y bitácora pública

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | Cualquier visitante autenticado o no puede ver el badge de la entidad (en revisión / Nivel 1 / Nivel 2) y el resumen de insumos cubiertos. |

#### RF-21 Control de acceso por rol

| Campo | Contenido |
|---|---|
| Prioridad | M |
| Descripción | Cada operación de escritura valida el rol. Un adoptante no publica animales. Un Nivel 2 no ve módulos de dinero (el sistema no los incluye). |

### 3.2 Requisitos no funcionales

#### RNF-01 Seguridad

El sistema almacena contraseñas con función de resumen (hash) y sal. Las sesiones expiran. Las evidencias documentales no son listables sin autenticación de validador o de la entidad dueña. En despliegue piloto se usará HTTPS.

#### RNF-02 Protección de datos personales

Cumplimiento mínimo de Ley 1581: consentimiento al registro, finalidad declarada, y derechos de consulta/corrección documentados en un texto breve. La bitácora pública de insumos no expone identificación del donante.

#### RNF-03 Usabilidad

Un usuario no técnico (refugio) debe poder publicar un animal y un ítem de deseos en un teléfono, sin manual, en menos de 10 minutos en prueba de usabilidad del piloto. El cuestionario de adopción no supera cinco preguntas iniciales.

#### RNF-04 Compatibilidad

La aplicación web funciona en las dos últimas versiones estables de Chrome, Firefox y Safari, en viewport móvil y escritorio.

#### RNF-05 Rendimiento (piloto)

El listado de hasta 200 animales publicados responde en menos de 3 segundos en el entorno de piloto, en condiciones normales de red.

#### RNF-06 Disponibilidad (piloto)

No se compromete SLA 24/7. El entorno de demostración debe estar disponible en la franja de sustentación acordada con el instructor.

#### RNF-07 Mantenibilidad

Código en repositorio Git, separado al menos en cliente, API y persistencia. Las reglas de especie y la ausencia de recaudo se aplican en la API, no solo en la interfaz.

#### RNF-08 Trazabilidad

Toda verificación, postulación, entrega y cobertura de ítem deja registro de fecha, actor y estado anterior/nuevo.

#### RNF-09 Idioma

Interfaz y mensajes de error en español de Colombia.

### 3.3 Requisitos de interfaces

#### 3.3.1 Interfaces de usuario

Tres superficies:

1. **Pública:** catálogo, perfil de animal, perfil de entidad (badge + bitácora).
2. **Adoptante / donante:** cuestionario, postulaciones propias, reservas de ítems.
3. **Entidad / validador:** tablero de animales, postulaciones, deseos y cola de verificación.

Los wireframes son el artefacto **2.4** (aún pendiente). Este ERS no los sustituye.

#### 3.3.2 Interfaces de hardware

No aplica hardware especializado. El usuario final usa computador o teléfono con navegador.

#### 3.3.3 Interfaces de software

Navegador + API propia + motor relacional + almacén de archivos. Sin pasarela. Sin API del IDPYBA.

#### 3.3.4 Interfaces de comunicación

HTTPS en piloto desplegado. JSON en la API. Carga de archivos (imágenes / PDF de evidencias) con límite de 5 MB por archivo (acordado con la arquitectura 2.1).
